1. Executive Summary & Problem Context

This document presents the complete technical architecture and implementation for the PERN Full-Stack Technical Case Study. The application models a real-world manufacturing and supply company distributing industrial products to commercial B2B clients.

The core workflow enforces strict sequential lifecycle integrity across five distinct stages:

Core Workflow Lifecycle:
Customer Enquiry (NEW → QUOTED → WON/LOST) ➔ Commercial Quotation (DRAFT → SENT → ACCEPTED/REJECTED) ➔ Sales Order (PENDING) ➔ Stock Reservation (CONFIRMED) ➔ Dispatch Fulfillment (DISPATCHED)

3. Role-Based Access Control (RBAC) Architecture

Authentication is secured using JSON Web Tokens (JWT) with passwords hashed via bcryptjs. Permissions are strictly enforced by the backend middleware:

Role Credentials Permissions & Capabilities
ADMIN admin@sathvika.com / Password123! Full system access: Manage inventory, confirm sales orders (atomically reserving stock), and process dispatch fulfillment.
SALES USER sales@sathvika.com / Password123! Register customers, log enquiries, generate commercial quotations, convert accepted quotes to sales orders, and view live stock. Restricted from confirming orders or dispatching.

4. Core Functional Workflow Implementation

4.1 Stage 1: Customer Enquiry

Captures customer requirements with target delivery dates, notes, and dynamic multi-product line items. Enquiries transition through statuses: NEW → QUOTED → WON / LOST. Supports both existing customer selection and inline onboarding of new commercial clients.

4.2 Stage 2: Commercial Quotation Engine

Quotations reference a specific customer enquiry. The backend engine acts as the authoritative source of truth for all mathematical calculations:

  • Line Amount Calculation: Line Amount = (Qty × Unit Price × (1 − Discount%)) × (1 + GST%)
  • Tax & Discount Aggregation: Computes Subtotal, Trade Discount, Taxable Base, and 18% GST.
  • Lifecycle Progression: DRAFT → SENT → ACCEPTED / REJECTED.

4.3 Stage 3: Quotation to Sales Order Conversion

Enforces two critical business rules mandated by the case study:

  1. Accepted Status Enforcement: Only ACCEPTED quotations can be converted into Sales Orders. Conversions from DRAFT or REJECTED statuses are rejected with 400 Bad Request.
  2. Duplicate Prevention: A 1-to-1 unique constraint prevents duplicate Sales Orders from being generated from the same quotation.

4.4 Stage 4: Inventory Reservation & Concurrency Race Condition Solution

When an Administrator confirms a Sales Order, the backend validates available stock: $$\text{Available Stock} = \text{Physical Quantity} - \text{Reserved Quantity} - \text{Damaged Quantity}$$

Concurrency Solution: To solve the simultaneous reservation challenge (e.g. User A requesting 80 units and User B requesting 50 units on available stock of 100), reservations are executed inside isolated Prisma database transactions: 

await prisma.$transaction(async (tx) => {
  const inv = await tx.inventory.findUnique({ where: { productId } });
  const available = inv.physicalQuantity - inv.reservedQuantity - inv.damagedQuantity;

  if (available < requiredQuantity) {
    throw new Error(`Cannot reserve more than available inventory.`);
  }

  // Atomically increment reserved stock; physical stock remains untouched
  await tx.inventory.update({
    where: { id: inv.id },
    data: { reservedQuantity: { increment: requiredQuantity } }
  });
});

Simultaneous conflicting requests are serialized: one request commits successfully, while the other receives an immediate 400 Bad Request. Over-allocation is mathematically impossible.

4.5 Stage 5: Dispatch Fulfillment

Admin dispatches confirmed orders by specifying the Vehicle Registration Number and Driver Name. Upon dispatch, both Physical Quantity and Reserved Quantity decrement simultaneously, finalizing the fulfillment cycle.

6. Live Verification Preparedness (Case Study Round 3)

  • Damaged Stock Extension: The damagedQuantity column is pre-modeled in the Inventory table. Available stock calculation dynamically subtracts damaged stock: Available = Physical − Reserved − Damaged.
  • Order Cancellation: POST /api/sales-orders/:id/cancel is implemented to safely return reserved stock to the available inventory pool when an order is cancelled.
